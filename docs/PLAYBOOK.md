# Ionic 3 → Bare React Native Porting Playbook

A reusable guide for converting the Basiq360 / Abacusdesk loyalty apps (Ionic 3 + Angular 5 + Cordova) into **bare React Native (TypeScript)**, fully on a local laptop, with no backend access needed while building.

- **Part A** – Instructions for an AI coding agent (paste/share this part to the agent).
- **Part B** – Step-by-step workflow with commands and code templates.
- **Part C** – Worked example: Top Bath (first app ported).
- **Part D** – Moving fast on the next projects.
- **Part E** – Learning notes: why each decision was made (interview prep).

---

## Part A — Instructions for the AI agent

> **For the Topbath port the source of truth is the implementation plan** (`docs/superpowers/plans/2026-10-29-topbath-rn-migration.md`): its **Global Constraints** section replaces the hard rules below where they differ, and its **S-task** (per-screen porting procedure) replaces A2 step 4 and B9. The design spec is `docs/superpowers/specs/2026-10-29-topbath-rn-migration-design.md`. The generic rules below remain a reusable baseline for other projects.

> You are porting an existing Ionic 3 / Angular 5 / Cordova mobile app to **bare React Native with TypeScript** (no Expo). Follow these rules exactly.

### A1. Hard rules
1. **Everything local.** Work only on the developer's laptop. No EAS, no cloud builds, no Expo account, no CI. Create a local git repo for history; **never add a remote, never push**.
2. **Straight conversion, not a redesign.** Keep identical:
   - API base URLs and endpoint paths
   - request body field names and shapes
   - headers (e.g. `Authorization` / `Token: Bearer <token>`)
   - local-storage keys and stored object shapes
   - role/user-type logic and which screens each role sees
   - validation rules and user-facing text
3. **Do not change security behaviour** (tokens, OTP flow, user IDs in requests). That is owned by another person. If something looks unsafe, copy it as-is and leave a comment:
   `// NOTE (security, not changed): <what you saw>`
4. **Comment every screen and every deviation.** Each screen file starts with a header naming its Ionic source. Wherever the RN code must behave differently from Ionic, add a comment explaining why.
5. **Never touch real data while developing.** Default runtime mode is `MOCK`. Only switch to `DEV`/`LIVE` when the developer explicitly asks.
6. **Don't search GitHub or external services unprompted.** Only use repos the developer gives you.
7. **Ask before** anything hard to reverse: setting environment variables, installing global tools, deleting files, changing the package ID.
8. **Verify before claiming done**: a screen is done only when it builds, renders in MOCK mode, and its API calls match the Ionic version.

### A2. Working order
1. Inventory the Ionic app (pages, endpoints, plugins, storage keys, roles) — Part B1.
2. Present a blueprint and wait for approval.
3. Phase 0 foundation, including **proving the APK → phone pipeline on day 1**.
4. Port screens phase by phase. After each phase: debug APK → install on phone → manual checklist → developer sign-off → next phase.
5. One local commit per screen (or small group of screens).

### B1. Inventory the Ionic app

Preferred: copy `scripts/ionic-inventory.sh` from the Top Bath RN project and run
`bash scripts/ionic-inventory.sh <ionic-repo>/src > docs/INVENTORY.md` (handles nested sub-pages, base URLs, storage keys, plugins, languages).

Manual equivalent — run from the Ionic repo's `src` folder (Git Bash):

```bash
# Pages: html lines | ts lines | endpoints each page calls
cd pages
for d in */; do d=${d%/}
  n=$(cat $d/*.html 2>/dev/null | wc -l); t=$(cat $d/*.ts 2>/dev/null | wc -l)
  e=$(grep -ohE "(onPostRequestDataFromApi|onGetRequestDataFromApi|post_rqst|get_rqst)\([^,]*,\s*['\"][^'\"]+['\"]" $d/*.ts 2>/dev/null \
      | grep -oE "['\"][^'\"]+['\"]$" | tr -d "'\"" | sort -u | tr '\n' ' ')
  echo "$d|$n|$t|$e"
done
# Folders with 0 lines contain sub-pages -> repeat the loop inside them.

cd ..
grep -n "Url\s*=" providers/dbservice/dbservice.ts      # base URLs
grep -rhoE "storage\.(get|set)\(['\"][^'\"]+" . | sort -u   # storage keys
grep -rhoE "import \{[^}]+\} from '@ionic-native/[^']+'" . | sort -u  # native plugins
```

Also read: `app/app.component.ts` (root page logic, push init), `pages/tabs` (role-based tabs), the registration-type page (roles), `assets/i18n/*.json`, `config.xml` (package id, permissions).

Record results in `docs/INVENTORY.md` in the RN project.

### B2. One-time laptop setup
- Node LTS (≥ 20), JDK 17, Android SDK (installed via Android Studio).
- SDK location: instead of a system-wide `ANDROID_HOME`, put it in the project's git-ignored `android/local.properties`, **with forward slashes** (a backslash is an escape character in `.properties`):
  `sdk.dir=C:/Users/<you>/AppData/Local/Android/Sdk`
  For one-off commands in Git Bash: `export ANDROID_HOME="C:/Users/<you>/AppData/Local/Android/Sdk"`.
- Licences accepted in the SDK → Gradle downloads missing platforms/build-tools itself (RN 0.88 needs SDK 37).
- Phone: Developer options → USB debugging ON. Check with `adb devices`.

### B3. Scaffold

```bash
npx @react-native-community/cli@latest init <AppName> --directory <folder> --package-name <com.client.app> --skip-git-init true
cd <folder> && git init && git config core.autocrlf false
```
Top Bath got React Native **0.88.1** / React 19.3 / TypeScript / New Architecture + Hermes. Record the version in `docs/PLAN.md`.

**Fix these right after scaffolding** (each one bit us on Top Bath):
1. **Kotlin folder:** `--package-name com.x.y` creates `android/app/src/main/java/com/com.x.y/`. Move the two `.kt` files to `java/com/x/y/`.
2. **npm name:** the CLI writes the Java package into `package.json` `name`; change it to a plain name like `topbath-rn`.
3. **Test package id + app name** in `android/app/build.gradle` (and delete `app_name` from `res/values/strings.xml`, otherwise "duplicate resource"):
```gradle
defaultConfig {
    resValue "string", "app_name", "Topsan"
}
buildTypes {
    debug {
        applicationIdSuffix ".rn"                  // installs next to the real Play Store app
        resValue "string", "app_name", "Topsan RN" // so you can tell them apart
    }
}
```
4. `android/local.properties` as in B2.
5. First commit, then **build the debug APK immediately** (B4) before adding any code.

### B5. Project structure

```

    mock/

```

### B7. Angular/Ionic → React translation cheat-sheet

| Ionic 3 / Angular | React Native |
|---|---|
| `@Component` class + template | function component returning JSX |
| class fields + `[(ngModel)]` | `useState` + `value`/`onChangeText` |
| `*ngIf="x"` | `{x && <View/>}` |
| `*ngFor="let i of list"` | `<FlatList data={list} renderItem=.../>` (virtualised) |
| `(click)` / `(tap)` | `onPress` on `Pressable`/`TouchableOpacity` |
| `ionViewDidLoad` | `useEffect(() => {...}, [])` |
| `ionViewWillEnter` / `ionViewDidEnter` | `useFocusEffect` |
| `navCtrl.push(Page, params)` | `navigation.navigate('Page', params)` |
| `navCtrl.setRoot(Page)` | `navigation.reset({ index: 0, routes: [{ name: 'Page' }] })` |
| `navCtrl.pop()` | `navigation.goBack()` |
| `ModalController` / `PopoverController` | screen with `presentation: 'modal'` or RN `<Modal>` |
| `LoadingController` | shared `<Loader>` / `ActivityIndicator` |
| `AlertController` | `Alert.alert(...)` |
| `ToastController` | `ToastAndroid.show(...)` or shared toast |
| `Events.publish/subscribe` | React Context or a tiny event emitter |
| Injectable service (DI) | module singleton or Context + hook (`useApi()`) |
| `ion-refresher` | `FlatList` `refreshing` + `onRefresh` |
| `ion-infinite-scroll` | `FlatList` `onEndReached` |
| pipes (`| date`) | helper functions (`formatDate(x)`) |
| `ion-segment` | own segmented control / top tabs |
| SCSS | `StyleSheet.create`, values from `theme/` |

### B8. Code templates

**`src/config/env.ts`**
```ts
// Runtime switch. MOCK = no network at all (default while porting).
export type Mode = 'MOCK' | 'DEV' | 'LIVE';
export const MODE: Mode = 'MOCK';

// Copied unchanged from Ionic providers/dbservice/dbservice.ts
export const URLS = {
  LIVE: { root: '<rootUrl from dbservice.ts>', sfa: '<rootUrlSfa from dbservice.ts>' },
  DEV:  { root: '<commented dev rootUrl>',     sfa: '<commented dev rootUrlSfa>' },
};
```

**`src/api/client.ts`** (port of `dbservice.ts`)
```ts
// Ported from: src/providers/dbservice/dbservice.ts
// Keeps the same method names, URLs, headers and body shapes so the backend sees no difference.
import { MODE, URLS } from '../config/env';
import { mockRequest } from './mock';
import { storage } from '../storage';

type Server = 'root' | 'sfa';

async function headers() {
  const user = await storage.get('userStorageData');
  // NOTE (security, not changed): header format copied exactly from Ionic.
  return {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${user?.token}`,
    Token: `Bearer ${user?.token}`,
  };
}

export async function onPostRequestDataFromApi(body: unknown, fn: string, server: Server = 'root') {
  if (MODE === 'MOCK') return mockRequest('POST', fn, body);
  const res = await fetch(URLS[MODE][server] + fn, { method: 'POST', headers: await headers(), body: JSON.stringify(body) });
  return res.json();
}

export async function onGetRequestDataFromApi(fn: string, server: Server = 'root') {
  if (MODE === 'MOCK') return mockRequest('GET', fn);
  const res = await fetch(URLS[MODE][server] + fn, { headers: await headers() });
  return res.json();
}
```

**`src/api/mock/index.ts`**
```ts
// MOCK backend: lets every screen run without server access.
// Response shapes are inferred from the fields the Ionic page reads (e.g. resp.data.karigar.points).
import { store } from './store';
type Handler = (body?: any) => any;

const handlers: Record<string, Handler> = {
  'app_karigar/karigarHome': () => ({ status: 'success', data: store.home() }),
  'app_karigar/saveCoupon': (b) => store.addCouponPoints(b.qr_code),  // write -> visible in history
  // ...one entry per endpoint found in the inventory
};

export async function mockRequest(method: string, fn: string, body?: any) {
  await new Promise(r => setTimeout(r, 300));            // simulate network delay
  const h = handlers[fn];
  if (!h) { console.warn('[MOCK] no handler for', fn); return { status: 'error', msg: 'mock missing' }; }
  return h(body);
}
```

**Screen skeleton**
```tsx
// Ported from: src/pages/<page>/<page>.html + .ts + .scss
// Endpoints: app_karigar/xxx (POST, root)
// Differences from Ionic: <none | explain>
import React, { useCallback, useState } from 'react';
import { FlatList, Text, View } from 'react-native';
import { useFocusEffect } from '@react-navigation/native';
import { onPostRequestDataFromApi } from '../../api/client';

export default function PageName({ navigation, route }: any) {
  const [list, setList] = useState<any[]>([]);
  const [loading, setLoading] = useState(false);

  useFocusEffect(useCallback(() => {               // = ionViewWillEnter
    setLoading(true);
    onPostRequestDataFromApi({ /* same body as Ionic */ }, 'app_karigar/xxx')
      .then(r => setList(r.data ?? []))
      .finally(() => setLoading(false));
  }, []));

  return (
    <FlatList
      data={list}
      refreshing={loading}
      keyExtractor={(i, idx) => String(i.id ?? idx)}
      renderItem={({ item }) => <View><Text>{item.name}</Text></View>}
    />
  );
}
```

### B9. Per-screen recipe (repeat ~100 times)
1. Read the page's `.html`, `.ts`, `.scss`.
2. List: inputs/params, endpoints + bodies, fields read from responses, navigation targets, native features used.
3. Add/extend mock fixtures for its endpoints.
4. Build the screen with the template above; reuse shared components.
5. Register the route in navigation.
6. Run in MOCK on emulator/phone; compare side-by-side with the Ionic app/screens.
7. Commit: `feat(screen): port <page>`.

|---|---|---|

| 1 Onboarding & auth | language, registration type, login, OTP, registration, terms, role tabs | can log in as every role (mock) |
| 2 Core loyalty | home, profile, scan, points, history, transactions, gifts/redeem, transfers, offers, notifications | scan → points → redeem flow works |

### B11. Testing
- **Jest unit tests** for `api/client.ts`: correct URL per server, headers present, body passed through unchanged, MOCK never calls `fetch`.
- **Mock store tests**: a write (e.g. coupon scan) changes the next read (points total).
- **Manual checklist per phase**, per role, on a real phone: every screen opens, every button navigates, every form validates, back button behaves, no red-screen errors, Android permissions prompt correctly.

### B12. Common pitfalls
- Hardware back button: Ionic handled it in `app.component.ts`; in RN use `BackHandler` only where Ionic had custom behaviour (e.g. exit confirm on home).
- Ionic `storage` stored objects; AsyncStorage stores strings → always `JSON.stringify`/`JSON.parse` in the wrapper.
- Android permissions (camera, location, storage, notifications on Android 13+) must be in `AndroidManifest.xml` **and** requested at runtime.
- `ngFor` over long lists → always `FlatList`, never `.map` inside `ScrollView`.
- Images from server URLs need explicit `width`/`height` in RN.
- Keep the Ionic `en.json` keys unchanged so translations keep working.
- Never commit keystores, `google-services.json` or `.env` files.
- **Agent permission checks:** Claude Code's auto mode may block downloading and running external binaries (e.g. `curl … bundletool.jar && java -jar …`). Don't work around it — ask the developer to run it themselves (`! <command>`) or approve it.
- **Running the *old* app needs a real login.** All these apps hit production and need an OTP. Get test accounts per role from the backend team before planning a side-by-side comparison; you can inspect an `.aab` (it's a zip) to see which server it talks to (`base/assets/www/build/main.js`).
- Imported-but-commented plugins (e.g. SQLite/Zip in Top Bath's `app.module.ts`) are dead code — check before porting them.

## Part C — Worked example: Top Bath (first app)

- **Source:** `Basiq360-Abacusdesk/Topbath_App_loyalty` — Ionic 3.9.5, Angular 5.2.11, Cordova, package `com.topsan.app` (brand Topsan), v0.1.5.
- **Size:** 95 page folders, 8 of which contain sub-pages -> **117 screens**; ~51 images; 4 languages (`en`, `es`, `hin`, `nep`); primary colour `#002d25`.
- **Scope:** all 117 screens, with feature flags: **61 live or push-only** (phases 1-5) and **56 dead behind flags** (phases 6-7: 16 unreachable loyalty pages, 40 SFA pages). Phase counts 7/22/11/15/6/16/40 (`docs/inventory.json`, spec section 6.1).
- **RN project:** `C:\Users\dhruv\Projects\topbath-rn` (RN 0.88.1), docs in its `docs/` folder.
- **Two backends:** loyalty `dd_api` (`app_karigar/*`, `app_master/*`) and SFA `crm/api/app` (`Checkin`, `Distributor`, `dealerData`, `Order`, `Attendence`, `TravelPlan`, `Leave`). A dev host exists but is commented out in `dbservice.ts`.
- **Roles at signup:** Plumber, Seller (`Sales_Boy`), Dealer, Sales Executive. Consumer is commented out. The Employee/SFA module (40 pages) is not reachable from the UI; it is ported behind the `sfa` feature flag (off for Topbath).

- **Native features:** QR scan, camera, files/upload, GPS + geocoding, navigation launch, share, in-app browser, video capture, push (Firebase), permissions.

- **Backend-dependent features (MOCK until access is given):** login OTP SMS, registration, coupon scan/save, redeem, point transfer, complaints, plumber check-in/out, sales-exec add, feedback/enquiry/survey, push, maps.

### Pilot lessons (Language pilot, plan Task 13)

a. Shared component gaps go to the kit on master first; the screen branch then rebases onto master.
b. Parity states must be reachable in production. A branch the shipped app can never reach (for example a state depending on a storage key the app reads but never writes, like `token`) is unit-tested only and gets no parity state. The card's **Storage keys** section flags these.
c. Diff % is not proof. The reviewer and the lead must look at both images and confirm they show the same state (the pilot's reference once showed the wrong state at 0.5%).
d. Ionic taps in the reference: drive the page's own handler inside NgZone when TapClick swallows synthetic events. RN taps go through `rnAction tap:<testID>`.
e. Capture RN at 360dp (emulator `wm density 480` on a 1080-wide device) with deviceVersion 15 for API >= 35.
f. Cold starts show the 6 s splash; capture uses the ready-wait plus a 5.5 s settle.
g. Worktrees: implementers code and run Jest in worktrees (junction `node_modules`); the lead merges to master and does all APK builds and emulator captures sequentially (one emulator, laptop memory).
h. HTTP error behaviour ("server error does nothing") is tested with a fixture variant `{ "$httpError": 500, "body": {} }` and `setFixtureVariant`, not a custom transport.

## Part D — Moving fast on the next projects

All Basiq/Abacusdesk loyalty apps come from the **same Ionic template** (same `dbservice.ts`, `app_karigar`/`app_master` endpoints, similar pages). So after the first app:

1. **Extract a starter kit** from the finished Top Bath RN app: `api/`, `storage/`, `i18n/`, `native/`, `components/`, `navigation/` skeleton, mock framework. Keep it as a local template folder.
2. **Diff, don't re-read.** For a new project, run the B1 inventory and compare with Top Bath's inventory:
   ```bash
   diff <(ls topbath/src/pages) <(ls newproject/src/pages)
   diff -r topbath/src/pages/home newproject/src/pages/home   # same page, what changed?
   ```
   - Identical pages → copy the RN screen, change branding only.
   - Slightly different → copy and patch the differences.
   - New pages → port with the B9 recipe.
3. **Rebrand via config:** app name, package id, colours, logo, base URLs, enabled roles — all in `config/` and `theme/`, not scattered in screens.
4. **Reuse mock fixtures**; most endpoints have the same names across clients.
5. Expect the second app to take a fraction of the first one's time; most of the effort becomes diffing and testing.

## Part E — Learning notes (why, not just how) — interview prep

### E1. Key decisions and the reasoning
| Decision | Why |
|---|---|
| **Rewrite screens, keep API contract** | The backend is the stable contract. Changing the client and the server at once doubles the risk; a pure client rewrite can be tested against the same server behaviour. |
| **Mock API layer behind one switch** | Unblocks development without backend access, avoids touching production data, makes demos and tests deterministic. This is the *adapter pattern* / *dependency inversion*: screens depend on an interface (`client.ts`), not on a concrete server. |
| **Stateful mocks (in-memory store)** | Static fixtures only test rendering; stateful mocks test *flows* (scan → points → redeem). |
| **Prove the APK pipeline on day 1** | *Risk-first ordering*: build tooling (Gradle, SDK, signing, device install) is the most likely thing to block you late. Fail early, cheaply. |
| **Phases with sign-off gates** | Small batches = fast feedback, easy rollback, visible progress. |
| **Bare RN instead of Expo** | Full control of native Android project, local Gradle builds, no account/cloud dependency; needed for many native modules. Trade-off: you maintain native config yourself. |
| **Same names as Ionic pages** | Traceability: anyone can map an RN screen back to its Ionic source; review is easier. |
| **Don't fix security during the port** | Separation of concerns and ownership: mixing a migration with behaviour changes makes bugs impossible to attribute. Flag, don't fix. |
| **One commit per screen** | Easy review, easy `git revert`, clear history. |

### E2. Concepts you should be able to explain
- **Ionic/Cordova vs React Native:** Ionic renders HTML/CSS in a WebView; Cordova plugins bridge to native. React Native renders *real native views*; JS talks to native through the bridge, and in the **New Architecture** through **JSI** (direct C++ calls), **Fabric** (renderer) and **TurboModules** (lazy native modules).
- **Angular vs React mental model:** Angular = classes, decorators, DI, two-way binding, RxJS. React = functions, hooks, one-way data flow, state lifting/Context.
- **Hooks:** `useState` (local state), `useEffect` (side effects), `useCallback`/`useMemo` (memoisation), custom hooks (reusable logic like `useApi`).
- **Lists & performance:** `FlatList` virtualises rows (renders only visible items) — the equivalent of fixing slow `ngFor` lists.
- **Navigation:** stack vs tabs vs modal; resetting the stack after login; passing params.
- **Permissions on Android:** manifest declaration + runtime request; Android 13 notification permission.
- **Build pipeline:** Metro bundles JS; Gradle builds the APK; debug vs release; signing with a keystore; `applicationId` and suffixes.
- **Testing pyramid:** unit (Jest) → integration (mock flows) → manual/E2E on device.

### E3. Practice interview questions (short answers)
1. **"How would you migrate a legacy hybrid app to React Native?"** — Inventory screens/endpoints/plugins; keep the API contract; build a foundation (navigation, API client, storage, i18n); add a mock layer; port in phases ordered by risk and dependency; verify each phase on a real device; release behind a different package id first.
2. **"How did you develop without backend access?"** — A mock adapter behind a single mode switch, with fixtures inferred from the fields the old client reads, and an in-memory store so write actions affect later reads.
3. **"How do you make sure nothing changes for the backend?"** — Port the HTTP service first with identical URLs, headers and bodies; unit-test that; screens only call that service.
4. **"Why bare RN over Expo?"** — Local builds, full native control, no cloud dependency; trade-off is more native maintenance.
5. **"How did you go faster on later apps?"** — Same template family: extracted a starter kit, diffed new apps against the first, copied identical screens, ported only differences.
6. **"What was hardest?"** — Typically native features (camera/QR, GPS, push, file upload) and matching platform behaviours (back button, permissions) — handled with thin wrappers in `native/` so screens stay simple.
7. **"How do you handle security issues you notice during a migration?"** — Document and escalate to the owner; don't silently change behaviour inside a migration.
